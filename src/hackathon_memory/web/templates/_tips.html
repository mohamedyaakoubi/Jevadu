The Hedera packages that the package files of the code name: the SDKs{{ parts.ref("sdk") }}, such as @hashgraph/sdk and @hiero-ledger/sdk, and other libraries, such as the Hedera Agent Kit or WalletConnect for Hedera. The ten named most often, among the projects whose code was read.

{% endcall %} {% call tip("winners-use", "What winners use, next to the others") %}

This puts facts side by side. It shows what winners used, not why they won, and it says nothing about a single project.

{% endcall %} {% call tip("order", "Order") %}

{% endcall %} {% call tip("event", "Event and prizes") %}

  • Winners' list only: its own page is no longer public, so it comes from the organiser's list of winners and has fewer details. Every project on such a list won a prize, but most winners still have their own page.

{% endcall %} {% call tip("proof", "Hedera proof") %}

Did the project really use Hedera? The parser finds the Hedera IDs on the project page and in its README: accounts{{ parts.ref("account") }}, topics{{ parts.ref("topic") }}, tokens{{ parts.ref("token") }}, smart contracts{{ parts.ref("contract") }} and single transactions. Each one is looked up on the public mirror node{{ parts.ref("mirror") }}.

  • Found: the ledger knows the ID as that kind of entity, created or used during the event.
  • Dates don't fit: it exists, but from another time.
  • Wrong kind of ID: the ledger knows the number as another kind of entity.
  • Empty ID: nothing ever happened with it, or the transaction failed.
  • ID not found: the ledger does not know it.
  • No ID given: neither the page nor the README names one. That is common, and says nothing bad about the project.

Every ID links to HashScan{{ parts.ref("explorer") }}, a public explorer of the same records.

{% endcall %} {% call tip("life", "Activity after the event") %}

Was the project still worked on after the event? Activity means a commit, or on-chain activity of the project's own IDs, more than 30 days after the event.

  • Active: activity in the last 90 days.
  • Quiet: activity, but none in the last 90 days.
  • Stopped: nothing more than 30 days after the event.
  • Too early to tell: the event ended less than 90 days ago.
  • Unknown: no commit dates, and no on-chain activity.
{% endcall %} {% call tip("ledger", "On the ledger") %}

What the public Hedera ledger{{ parts.ref("ledger") }} shows for each ID named on the page or in the README, read from a mirror node{{ parts.ref("mirror") }}. No AI.

Testnet{{ parts.ref("testnet") }} and mainnet{{ parts.ref("mainnet") }} are separate networks: the same number is a different entity on each. Every ID links to HashScan{{ parts.ref("explorer") }}.

{% endcall %} {% call tip("story", "Hedera services: page, code and ledger") %}

For each Hedera service, three sources side by side, with no AI:

  • Page: the words of the project page that name the service, such as “HCS” or “topic ID” for the Consensus Service{{ parts.ref("topic") }}, “HTS” for the Token Service{{ parts.ref("token") }}, or “smart contract” and “Solidity” for smart contracts{{ parts.ref("contract") }}. Never the AI summary. Each word is a button: it marks where the page says it.
  • Code: whether its code calls the service, from the reading of the code below: a source file that names one of the service's SDK classes, such as TokenCreateTransaction. A package alone never counts. “EVM setup” means that the code points EVM tools such as Hardhat at Hedera, as most Solidity projects do; that is not a call by itself.
  • Ledger: the transactions of its own Hedera IDs, read from a mirror node{{ parts.ref("mirror") }}, from 30 days before the event to 30 days after it.

Its own IDs are those whose kind fits the page and that no other project names: an ID that several projects name is often a shared service. HBAR is not compared: nearly every project moves HBAR to set itself up.

The ledger shows only the IDs that the page gives, and a team can use a service through an ID that it never names. A difference is a fact to look at, not a fault.

{% endcall %} {% call tip("story-readme", "Hedera services: README, code and ledger") %}

The same comparison as on the card of a project, for the submission:

  • README: the words of its README that name a Hedera service, such as “HCS” for the Consensus Service{{ parts.ref("topic") }} or “HTS” for the Token Service{{ parts.ref("token") }}. Each word is a button: it marks where the README says it, in the lines under the table.
  • Code: whether its code calls the service, from the reading of the code below. A package alone never counts, and “EVM setup” means that the code points EVM tools such as Hardhat at Hedera, which is not a call by itself.
  • Ledger: the transactions of the README's IDs whose kind fits, read from a mirror node{{ parts.ref("mirror") }} during the check and kept for 7 days: in the time of the hackathon and 30 days on each side, or every transaction when no hackathon is chosen.

The ledger shows only the IDs that the README gives, and a team can use a service through an ID that it never names. A difference is a fact to look at, not a fault.

{% endcall %} {% call tip("code", "Code") %}

The repository{{ parts.ref("repository") }} linked from the page, with its creation date and its last push, from GitHub.

{% endcall %} {% call tip("hedera-code", "Hedera in the code") %}

We read every file of the project's own code once, from the archive of its default branch on GitHub{{ parts.ref("repository") }}, and keep only what we find, with no AI: the Hedera packages that its package files name, the Hedera services that it calls (by the class names of Hedera's SDKs{{ parts.ref("hedera") }}, such as TopicCreateTransaction), other signs such as Hedera's JSON-RPC relay, a Hedera chain ID, a Hedera network of viem, wagmi or Hardhat, Hedera's system contracts or the mirror node{{ parts.ref("mirror") }}, the files that import a Hedera library, and the files that only name Hedera. Each file opens on GitHub as it was read.

Folders of other people's code, such as node_modules, are skipped, and .env files are never opened. This shows what the code names, not whether it runs, and it cannot see Hedera used from another repository.

{% endcall %} {% call tip("page", "From the project page") %}

The team's own text, copied verbatim from the project page as it was on the day it was saved. Not edited by AI.

{% endcall %} {% call tip("model", "AI summary") %}

Gemini 3.1 Pro read the project page and filled these fields. Each field has a label:

  • Stated: a sentence of the page says it.
  • Inferred: put together from several sentences; read it with more care.
  • Not found: the page does not say.

Under each field are the quotes it rests on. Every quote was checked against the page, and a field whose quotes were not found is hidden.

{% endcall %} {% call tip("compare", "Compared with your idea") %}

Written by Gemini 3.8 Flash{{ parts.ref("gemini") }} from the texts named under it: what is the same as your idea, and what is different. It does not judge the project.

{% endcall %} {% call tip("check", "Check a submission") %}

For judges, or for a team before it submits. Enter the GitHub repository, and the hackathon if you want the dates checked.

  • The check asks GitHub's API for the repository, its README, its newest commit and the archive of its code, one request after the other, with the name of this site. What was read before is not asked again.
  • It finds the Hedera IDs in the README, looks each one up on the public mirror node{{ parts.ref("mirror") }}, and checks the dates against the hackathon.
  • It reads the code for Hedera: its packages, its imports and its calls to Hedera services. A repository that was never read takes a few seconds, at most 30.
  • It shows whether the same repository or ID appeared at an earlier event, and the most similar past projects.

Facts only: no AI-generated text. You can then register the submission on Hedera{{ parts.ref("topic") }}.

{% endcall %} {% call tip("seen", "Linked projects") %}

Two projects are linked when they share a repository{{ parts.ref("repository") }}, or a Hedera ID on the same network that the ledger confirmed for both. Exact matching, no AI.

  • An ID that many teams use is most likely a shared service, such as a common test account or a public payment address: more than three different repositories in all, or two at one hackathon. Such an ID links nothing.
  • A shared name links nothing either: two teams can pick the same name.
{% endcall %} {% call tip("closest", "Most similar past projects") %}

The past projects closest in meaning to the README, found with the same semantic search as an idea (Google's embedding model{{ parts.ref("embedding") }}). Similar does not mean copied: the site shows facts, and people judge.

{% endcall %} {% call tip("register", "Public register") %}

A list of records in one topic{{ parts.ref("topic") }} on Hedera testnet{{ parts.ref("testnet") }}. Each record says: this repository was registered for this hackathon. Hedera stamps it with a sequence number and a consensus time that nobody can change.

  • The topic has no admin key, so nobody can delete the register or change its rules, this site included. Only the site's own account can write to it.
  • A record holds hashes only: 64-character fingerprints of the repository link and of the account. The same link always gives the same hash, and the hash does not reveal the link.
  • It shows when a repository was registered, not who registered it. When the same repository comes back for another hackathon, the check shows the first date.
{% endcall %} {% call tip("hackathon", "Hackathon (optional)") %}

This site is a memory of past hackathons, not a live view: it cannot see the other submissions of a hackathon that is running now.

  • None: the check shows each fact with its own date, for example "token created 7 March 2026", and you judge.
  • A hackathon, or its dates: the check also says whether each Hedera ID was created or used during the event, and whether the code changed after it.

The list shows the hackathons running now first, then past ones by the year they ended. Registering on Hedera needs a hackathon from the list.

{% endcall %} {% call tip("check-compare", "Compare with Gemini") %}

Gemini 3.8 Flash{{ parts.ref("gemini") }} reads this README and the summaries of the most similar past projects, and writes what each one shares with it and how it differs. It does not judge any project, and it never calls anything a copy.

It costs less than one cent, and the answer is cached for one day, so the same check does not call Gemini again.

{% endcall %} {% call tip("insights", "Insights") %}

A few facts in sentences, counted live from the same list as the charts. Each one names its numbers, and none of them predicts, scores or ranks a project. A sentence appears only when the list holds enough projects for it.

  • Won again: linked projects (the same repository, or the same Hedera ID confirmed by the ledger) that each won a Hedera prize, at more than one event. A link says only that.
  • Categories with the most Hedera prizes: the categories are chosen by Gemini 3.1 Pro from each page, so an entry from a winners' list has none.
  • Still worked on after the event: active or quiet, among the projects whose activity is known 90 days after their event; each group needs at least 20 such projects.
